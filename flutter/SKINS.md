# Skins

A skin changes how the M12 puzzle **looks**, never what it **does**. However
elaborate a pack's swap animation is, the engine still executes one atomic
`mathieu_swap()`; the path is cosmetic. Packs supply appearance, the engine
supplies the group.

Purpose: the physical toy ships with a booklet linking to an app that looks like
the toy, so the app can do the tutorial things a mechanical toy cannot. See
`MACROS.md` for that half.

> **Disclosure.** Some packs are derived from physical toy designs that are
> held back. This file is tracked and must stay free of device mechanism
> — no routing, no device dimensions, no toy-repo file paths. The mechanism half
> of the documentation lives with the packs themselves, in the gitignored
> `lib/skin/packs_private/DEVICE-PACKS.md`. See **Disclosure gate** below; the
> timing decision is Scott's, not this document's.

## Layout

    lib/skin/skin.dart                 the six facets + Skin
    lib/skin/board_metrics.dart        SkinGeometry (ratios) + BoardMetrics (resolved layout)
    lib/skin/registry.dart             the pack table
    lib/skin/packs/default_pack.dart   today's appearance — ships always
    lib/skin/packs_private/            device-derived packs — GITIGNORED (see below)
    lib/skin/registry_packs.g.dart     GENERATED by tool/gen_skin_registry.sh — public packs only

`test/packs_private/` is gitignored for the same reason: it imports the packs,
so it could not compile in a clone that has none.

Consumers: `lib/ball_ring.dart` (the board) and `lib/swap_preview.dart` (the
settings-page preview). Both go through `BoardMetrics` and `SkinPainter`, so a
pack cannot be applied to the game and silently leave the preview classic.

## The six facets

| Facet | What it owns |
|---|---|
| `SkinVocabulary` | what the machine calls its parts; the three on-board control labels |
| `SkinPalette` | board, piece colours, numeral, seat tag, chrome/dim/accent, optional deck base |
| `SkinGeometry` | pure ratios against half the board width — piece radius, ring inset, outboard gap, tag inset, fonts, start angle, direction |
| `SkinPainter` | `paintBoard` (furniture), `paintPiece`, `paintOverlay`, numeral/tag styles |
| `SkinMotion` | five durations, per-kind curve, `piecesTravel`, and `markPath` — the travel path |
| `SkinSound` | remaps sound names onto the shared set |

A full pack is roughly 120 lines of Dart; a re-colour about 40.

Every pack so far lands in a narrow band around the default's
`pieceR/ringR = 0.190` with an outboard gap of 2.5 piece radii, which is why one
layout routine serves them all. A pack states its own ratios in its own file.

## Writing a pack

A pack is one file, `<id>_pack.dart`, exposing a single entry point:

```dart
Skin buildSkin() => const MyPackSkin();
```

Put it in `lib/skin/packs/` (ships always) or `lib/skin/packs_private/` (gated
and gitignored), then run `tool/gen_skin_registry.sh` and rebuild. Nothing else
in the app changes: drop the directory in, generate, build; delete it,
generate, build, and it is gone. That is the droppable requirement.

**Rules:**

1. **No assets.** `pubspec.yaml` declares `assets/images/` and `assets/sounds/`
   as *directory globs*, so anything dropped there is swept into every build,
   including the public web build — the flag would gate the code but not the
   art. Draw procedurally with `Canvas`; if a pack truly needs a bitmap, embed a
   base64 `Uint8List` const inside its own `.dart` file, which then tree-shakes
   with the pack.
2. **Distinctive id.** The id must be a token that cannot occur by accident in a
   compiled bundle, because `tool/check_no_device_skins.sh` greps for it. Bare
   `transfer` already appears twice in a clean web bundle and six times in a
   clean `.apk`; the transfer-ring pack is therefore `transfer_ring`.
3. **`sensitive => true`** for anything device-derived.
4. Packs are pure Dart classes, not JSON. Painting is code, and Flutter web has
   no dynamic code loading, so a JSON pack could only ever change data, never
   draw. Keeping the whole pack in Dart is also what makes tree-shaking the
   disclosure mechanism — JSON assets are not tree-shaken, they ship.

## The registry, and why there are two generated files

`tool/gen_skin_registry.sh` writes **two** outputs, and the split is
load-bearing:

| file | tracked? | contains |
|---|---|---|
| `lib/skin/registry_packs.g.dart` | **yes** | public packs only — never names a private pack, even on a machine that has them |
| `lib/skin/packs_private/main_private.dart` | no (inside the ignored dir) | an alternative Flutter entry point that imports the private packs |

An earlier version emitted the private imports into `registry_packs.g.dart`
itself. That file is tracked, so committing it from the one machine that holds
the private packs broke **every other clone**:

    error • Target of URI doesn't exist: 'packs_private/flatpack_pack.dart'
    error • Target of URI doesn't exist: 'packs_private/marbles_pack.dart'
    error • Target of URI doesn't exist: 'packs_private/transfer_ring_pack.dart'

— failing `flutter analyze`, `flutter test`, the web build, CI and the Xcode
App Store archive, and leaking the pack names into the public tree besides.
`web/deploy.sh` regenerates before building, so deploys self-healed and hid it.

The fix is the entry-point split. `lib/main.dart` exposes the seam:

```dart
Future<void> runMathieu({void Function()? registerExtraSkins}) async { … }
void main() => runMathieu();
```

The default entry point registers the public packs and nothing else. A build
that wants a private pack targets the generated private entry point instead:

    flutter build web -t lib/skin/packs_private/main_private.dart \
                      --dart-define=SKIN_FLATPACK=true

**Do not merge the two generated files back together.** The invariant is that
no tracked file may name, import, or otherwise reference anything under
`packs_private/`. `tool/check_no_device_skins.sh --source` enforces it.

## Gated packs — HOLD

The device-derived packs are held back and cannot ship by accident: the default
entry point cannot reach a private pack, because the import does not exist in
the tracked tree, and `tool/check_no_device_skins.sh` fails the build if one
ever appears. Every public artifact contains the classic skin and nothing else.

Releasing a pack is a deliberate one-line action (`--dart-define=SKIN_<ID>=true`
with the private entry point) and is **Scott's call alone**. Until then: do not
run `web/deploy.sh` with a `SKIN_*` define, and do not commit anything under
`packs_private/`.

Booklet deep links are safe to print today regardless: a link naming a pack that
is not present degrades **silently** to the default skin (see below), so URLs
such as `…/m12/#skin=flatpack&lesson=6` are stable now.

## Default fidelity

The default pack must stay pixel-identical to the pre-skin app.

- `test/ball_ring_golden_test.dart` and `test/swap_preview_golden_test.dart`
  hold goldens **captured from the pre-skin renderer**, at three board sizes,
  at rest and mid-swap and mid-rotation.
- `test/skin_fidelity_test.dart` re-implements each legacy expression verbatim
  and demands *exact* equality.
- `test/macro_key_ui_test.dart` covers what the goldens cannot see: they render
  `BallRing` alone, so nothing else notices if the screen *around* the ring
  changes. It asserts the board at rest still shows two counter lines.

Two legacy quirks are preserved on purpose and are load-bearing:

- the piece radius is `(ratio * halfWidth).roundToDouble()` on the board but
  **unrounded** in the preview;
- the preview draws its numerals at `0.85 × pieceR` while the board uses `0.80`.

The centre Swap/Left/Right block is still absolute pixels
(`controlWidth: 190`, `controlTopOffset: -44`) rather than piece-radius
multiples. Converting it changes the layout, so it cannot ride along with a
pixel-faithful refactor — it is a deliberate follow-up, and a pack that rescales
the ring should override both. Under the `flutter_test` font that fixed 190pt
row overflows by 23px; it fits on device, and the golden and widget tests
consume the exception deliberately.

### Two intended departures from the pre-skin screen

The board is pixel-identical; the screen around it gained exactly one thing.

- **A "Learn" action in the AppBar** (`school_outlined`, left of Settings). This
  is the entry point to the tutorial, which is the whole reason the app exists
  alongside the toy. There is no way to ship the feature without a way in.
- The distance-from-home read-out is a *third* counter line, and it is
  suppressed when it would read zero — so a board at rest still shows the two
  lines the original had.

## Not covered

`watch/` is a second, independent SwiftUI renderer sharing only the C ABI. It
gets no skin system: its palette is re-declared in `watch/Sources/Palette.swift`,
its geometry re-derived in `watch/Sources/GameView.swift`, and its marble
already diverges from Flutter's. "The default skin" is therefore not one thing
across the fleet today. `Apple/DeviceIndependent/` is the historical source of
the look — read for fidelity, do not skin.

Note that `watch/project.yml` compiles `../flutter/native/mathieu_ffi.cpp`
directly, so C-side behaviour changes reach the watch even though the UI does
not. See `MACROS.md` on the `mathieu_set_macro` semantics change.
